# neo-browser 아키텍처 (초안)

개발자용 AI 전용 브라우저의 첫 버전 설계입니다. Electron과 TypeScript로 만들고, Linux를 먼저 지원한 뒤 macOS로 넓힙니다.

이 저장소의 Chrome 확장을 Electron 앱으로 교체했습니다. 확장 코드는 git 기록에 남아 있습니다.

## 차별점

다른 제품과 구분되는 점은 네 가지이며, 모두 프롬프트가 아니라 코드로 강제합니다.

1. **작업별 로그인 격리:** 작업은 허용된 로그인만 볼 수 있습니다.
2. **외부 전송 통제:** 작업은 허용된 사이트로만 데이터를 보낼 수 있습니다.
3. **연결 방식과 무관한 동일 규칙:** 내장 에이전트와 외부 에이전트(MCP/CLI)가 같은 검사를 거칩니다.
4. **Linux 우선 지원**

## 스파이크로 확인한 것

코드는 별도 저장소 `~/neo-browser-spike`에 있습니다.

| 항목 | 결과 |
|---|---|
| 세션 격리와 전송 차단 자동 테스트 | Linux, 샌드박스 켬: 통과 41, 실패 4, 판정 불가 4, 참고 3 |
| Google, GitHub 실제 로그인 | macOS, 집 인터넷, 기본 User-Agent: 성공 (사용자 보고) |
| 로그인 쿠키를 작업 세션으로 복사 | GitHub 성공 (16/16), Google 실패 (15/15 복사 후에도 재로그인 요구, 원인 미상) |

실패 4건은 대응 방법까지 설계에 반영했습니다.

| 실패 | 대응 |
|---|---|
| raw CDP `Target.getTargets`로 다른 세션의 페이지가 보임 | CDP 허용 목록 |
| raw CDP로 다른 세션 페이지에 연결해 HttpOnly 쿠키를 읽음 | CDP 허용 목록 |
| CDP `loadNetworkResource`가 요청 차단을 우회함 | CDP 허용 목록 + 허용 목록 프록시 (스파이크에서 프록시가 차단함) |
| WebRTC STUN이 요청 차단을 우회함 | WebRTC UDP 정책 (스파이크에서 정책이 차단함) |

아직 모르는 것:

- **Linux에서의 실제 로그인:** 이 서버에는 화면이 없어 아직 해 보지 못했습니다.
- **로그인 유지:** 시간이 지나도 유지되는지, 나중에 차단되지 않는지 모릅니다.

## 전송 통제 측정 결과

`npm run e2e:security`가 실제 작업 세션(`src/main/task-session.ts`)으로 측정합니다. 각 경로는 통제 없는 대조 세션에서도 실행해, 대조에서 도달하지 않은 경로는 통과로 치지 않습니다.

| 경로 | 결과 |
|---|---|
| fetch, XHR, beacon, 이미지, 스크립트, iframe, 폼, WebSocket, 워커, 서비스 워커, 페이지 이동 등 | 차단됨 |
| raw CDP `Page.navigate`, `Network.loadNetworkResource` | 차단됨 |
| WebRTC STUN | 차단됨 |
| WebTransport (호스트, IP, 워커, blob, srcdoc) | 차단됨 |
| DNS 조회 (dns-prefetch, 차단된 fetch) | 차단됨 (프로세스 전체 스위치) |
| preconnect, speculation prefetch | **판정 불가:** 대조 세션에서도 canary에 도달하지 않음 |

판정 불가인 두 경로도 나간다면 프록시를 거칠 것으로 보이지만, 직접 확인한 것은 아닙니다.

전송 통제로 막지 못하는 것도 있습니다.

- **허용된 사이트로 보내는 데이터:** 허용한 사이트로는 무엇이든 전송할 수 있습니다.
- **다른 로컬 프로그램:** 프록시는 로컬 포트라서 같은 컴퓨터의 다른 프로그램도 쓸 수 있습니다. 다만 허용된 호스트에만 연결됩니다.

## 구조

```text
Electron 메인 프로세스
├─ 화면(shell): 작업 목록, 승인 창, 로그인 화면
├─ TaskManager: 작업 생성과 종료
│   └─ Task (작업마다 하나)
│       ├─ Session: 전용 partition
│       ├─ 전송 통제: 요청 차단 + 허용 목록 프록시 + WebRTC 정책 (DNS 차단은 프로세스 전체)
│       ├─ 페이지: 샌드박스된 WebContentsView (preload 없음)
│       ├─ GatedCdp: 허용된 CDP 명령만 통과
│       └─ ToolExecutor: policy 검사와 사용자 승인
├─ 내장 에이전트: agent 루프 → ToolExecutor
└─ 외부 연결 서버: 권한 0600 Unix 소켓 → ToolExecutor

외부 에이전트 → MCP/CLI 브리지 → Unix 소켓
```

내장 에이전트와 외부 에이전트는 모두 `ToolExecutor`로만 브라우저를 조작합니다. 차별점 3은 이 구조로 보장합니다.

## 보안 규칙

기존 `CLAUDE.md`의 불변식(안전 검사는 코드에, 페이지 내용은 신뢰하지 않음 등)을 그대로 유지하고, 다음을 추가합니다.

- **raw CDP는 어디에도 노출하지 않습니다.** 모델과 외부 에이전트는 물론 내부 코드도 `GatedCdp`로만 보냅니다. 허용 목록은 `browser.ts`가 실제로 쓰는 명령으로 시작하며, `Target.*`, `Network.loadNetworkResource`, `Storage.*`는 넣지 않습니다.
- **`Runtime.evaluate`와 `Runtime.callFunctionOn`은 내부 고정 코드만 실행합니다.** 임의 코드 실행을 도구로 제공하면 전송 통제를 페이지 안에서 시도할 수 있으므로 첫 버전에는 넣지 않습니다.
- **전송 통제는 네 겹을 모두 켭니다.** 요청 차단, 프록시, WebRTC 정책, DNS 차단입니다. 요청 차단만으로는 뚫리는 경로가 있었습니다. 프록시를 설정하지 못하면 작업을 시작하지 않습니다.
- **Chromium 네트워크(Electron의 `net`, `session.fetch`)는 이름을 해석할 수 없습니다.** DNS 차단이 프로세스 전체에 적용되기 때문입니다. 메인 프로세스의 통신은 Node를 사용합니다.
- **승인은 앱 화면에서만 받습니다.** 외부 에이전트는 승인을 요청할 수만 있고, 응답할 수 없습니다.
- **로그인 중에는 에이전트를 멈춥니다.** 사용자가 작업 창에서 로그인하는 동안 도구 호출을 거부합니다. 비밀번호 입력란 차단은 `policy.ts`의 규칙을 유지합니다.
- **쿠키 값은 기록하지 않습니다.** 로그에는 개수와 이름만 남깁니다.
- **`--no-sandbox`로 배포하지 않습니다.**
- **API 키는 메인 프로세스에만 둡니다.** `safeStorage`로 암호화하되, Linux에 키링이 없으면 약한 저장 방식(`basic_text`)이 선택될 수 있습니다. 이 경우 조용히 저장하지 않고 사용자에게 알립니다.

## 로그인 방식

| 방식 | 동작 | 용도 |
|---|---|---|
| 작업 안에서 직접 로그인 (기본) | 빈 임시 세션에서 사용자가 로그인 | 모든 사이트 |
| 저장 프로필 (선택) | `persist:` partition에 로그인과 허용 호스트를 남겨 재사용 | 매번 로그인하기 번거로운 경우 |

- 기본 작업 세션은 메모리에만 있어서 작업이 끝나면 로그인이 사라집니다.
- 직접 로그인은 스파이크의 첫 로그인과 같은 조건(빈 세션)입니다. 다만 Google에서 반복 로그인이 추가 인증을 부르는지는 아직 확인하지 않았습니다.
- 쿠키 복사는 Google에서 실패했고 저장 프로필로 비슷한 격리를 얻을 수 있어 3단계에서 뺐습니다. [idea.md](../idea.md)에 후보로 남깁니다.

## 3단계 설계: 로그인

인터뷰로 정한 방향입니다. 임시 세션을 기본으로 두고, 사용자가 켠 로그인 모드에서만 전송 통제의 호스트 제한을 잠시 풀며, 그동안 에이전트는 멈춥니다.

### 로그인 모드 상태

| 상태 | 허용 범위 | 다음 상태 |
|---|---|---|
| 일반 | 허용 목록의 호스트 | 사용자가 시작하면 개방 |
| 개방 | 모든 공인 호스트와 허용 목록 | 5분간 입력이 없거나 화면이 잠기면 동결, 완료하거나 30분이 지나면 호스트 선택, 취소하면 일반 |
| 동결 | 동결 시점까지 접속한 호스트와 허용 목록 | 사용자가 다시 열면 개방, 완료하거나 30분이 지나면 호스트 선택, 취소하면 일반 |
| 호스트 선택 | 동결과 같음 | 사용자가 고르면 일반 |

- **30분 상한:** 개방을 시작한 시각부터 잽니다. 동결 중에도 줄어들고, 다시 열어도 늘어나지 않습니다.
- **동결의 목적:** 휴대폰 2단계 인증을 기다리는 페이지를 끊지 않으면서, 자리를 비운 동안 새 호스트가 열려 있지 않게 합니다.
- **결정 위치:** 상태와 허용 판단은 `src/egress.ts`의 순수 코드에 두어 요청 차단과 프록시가 같은 결정을 씁니다.
- **열린 연결:** 로그인이 끝나면 허용되지 않은 호스트로 열린 프록시 연결을 끊습니다. 그러지 않으면 로그인 중에 연 WebSocket이 계속 데이터를 보낼 수 있습니다.
- **화면 잠금과 절전:** 시스템 유휴 상태를 5초마다 조회해 `locked`이면 동결하고, 절전에 들어갈 때도 동결합니다.
- **그대로 유지되는 통제:** 프록시, WebRTC 정책, DNS 차단, 다운로드 차단, 권한 거부는 어떤 상태에서도 꺼지지 않습니다.
- **로컬 대상 제외:** 개방은 공인 호스트에만 적용합니다. 그러지 않으면 로그인 페이지의 스크립트가 개발 서버와 사설망에 닿을 수 있습니다. 호스트 이름이 아닌 프록시가 해석한 IP로 판단해 DNS 재바인딩도 막습니다.

### 시작

두 경로 모두 사용자의 동작 없이는 시작되지 않습니다.

- **사용자 버튼:** 에이전트가 실행 중이 아닐 때 패널에서 시작합니다.
- **`request_login` 도구:** 에이전트가 로그인 화면을 만났을 때 호출합니다. 인자는 받지 않고, 메인 프로세스가 현재 페이지의 실제 호스트를 승인 창에 표시합니다. 페이지가 모델을 조종해 피싱 페이지로 유도할 수 있으므로, 모델이 쓴 문구는 승인 창에 넣지 않습니다.

시작할 때 다음 순서로 준비합니다.

1. `https`인지 확인합니다. 루프백만 예외입니다.
2. 디버거를 분리합니다. 모델과 CDP가 로그인 화면을 읽지 못하게 합니다.
3. 페이지를 `about:blank`로 비우고 서비스 워커를 정리합니다. 앞선 페이지의 코드가 개방 시간을 이용하지 못하게 합니다.
4. 전체 개방으로 바꾸고 시작 주소를 엽니다.

### 진행 중

- **에이전트:** `request_login` 호출은 로그인 모드가 끝날 때까지 기다립니다. `ToolExecutor`는 로그인 중의 다른 도구 호출을 거부합니다. 5단계의 외부 에이전트도 같은 검사를 거칩니다.
- **주소 표시:** 패널은 현재 호스트를 항상 보여 주고, 패널과 호스트 목록에는 페이지 유래 문자열을 `textContent`로만 넣습니다.
- **팝업:** 로그인 모드에서만 같은 세션의 샌드박스 창으로 엽니다. preload는 없고 DevTools는 꺼져 있으며, 창 제목에 실제 주소를 표시합니다. 로그인 모드가 끝나면 닫고, 에이전트 실행 중에는 지금처럼 새 창을 막습니다.
- **패스키:** 보장하지 않습니다. 비밀번호, OTP, 휴대폰 인증을 대상으로 합니다.
- **입력 감지:** 페이지와 팝업의 입력으로 유휴 시간을 초기화합니다.

### 종료

- **호스트 선택:** 로그인 중 접속한 호스트 목록을 보여 줍니다. 시작한 호스트만 미리 체크하고 나머지는 사용자가 고릅니다. 고른 호스트만 허용 목록에 남습니다.
- **쿠키:** 호스트 선택이나 취소와 관계없이 이미 받은 쿠키는 세션에 남습니다.
- **에이전트 재개:** 디버거를 다시 연결하고 새 `CdpBrowser`를 만듭니다. 이전 ref는 쓸 수 없습니다.
- **모델에 보내는 결과:** 완료, 거절, 취소, 시간 초과와 현재 URL만 영어로 보냅니다. 시간 초과 때는 사용자가 호스트를 고른 뒤 결과를 보냅니다.

### 저장 프로필

- **저장 내용:** 쿠키와 저장소는 `persist:profile-<uuid>` partition에, 이름과 허용 호스트는 `userData/profiles.json`에 저장합니다.
- **허용 호스트:** 사용자가 허용한 호스트만 저장합니다. 작업을 시작할 때 패널에 표시하고 사용자가 뺄 수 있습니다.
- **에이전트 승인과의 관계:** 저장된 호스트는 전송만 허용합니다. 에이전트가 그 호스트로 이동하려면 실행마다 지금처럼 `ToolExecutor`의 승인을 받습니다.
- **선택 화면:** 패널에서 임시 세션이나 프로필을 고릅니다. 바꾸면 사용자에게 확인한 뒤 현재 작업과 대화를 버리고 새 `Task`를 만듭니다. 한 작업의 로그인 경계는 중간에 바뀌지 않습니다.
- **활성화 조건:** 쿠키 암호화 fuse가 켜져 있고 `settings.ts`의 `canEncrypt()`가 참일 때만 프로필을 쓸 수 있습니다. 아니면 이유를 안내하고 프로필 기능을 끕니다.
- **생성 시 안내:** 프로필을 만들 때 쿠키만 암호화되고 localStorage와 캐시는 디스크에 평문으로 남는다고 알리고, 사용자가 확인해야 만듭니다.
- **fuse 적용:** `npm install`이 `scripts/enable-cookie-encryption.mjs`로 fuse를 켜고, 6단계 패키지에도 같은 설정이 필요합니다. 앱은 실행 중에 실행 파일의 값을 읽어, 꺼져 있으면 프로필을 끕니다. macOS는 실행 파일을 고치면 서명을 다시 해야 하며, 이 경로는 아직 시험하지 않았습니다.
- **삭제:** 세션 데이터를 지우고 삭제 표시를 남긴 뒤, 다음 시작 때 세션을 열기 전에 partition 폴더를 지웁니다.
- **동시 사용:** 창 하나에 작업 하나이므로 3단계에서는 생기지 않습니다. 4단계에서 정합니다.

### 이 설계로 막지 못하는 것

- **개방 중의 전송:** 로그인 페이지의 스크립트는 공인 호스트 어디로든 데이터를 보낼 수 있습니다. 앞선 페이지를 비우는 것은 이전 데이터를 보호할 뿐, 사용자가 입력한 비밀번호를 그 페이지로부터 지키지는 못합니다.
- **피싱:** 승인 창과 주소 표시로 호스트를 보여 주지만, 판단은 사용자가 합니다.
- **프로필 안의 공유:** 같은 프로필의 작업은 쿠키와 저장소를 공유합니다. 앞선 작업의 페이지가 저장소에 남긴 내용이 다음 작업에 영향을 줄 수 있습니다.
- **디스크의 프로필 데이터:** 쿠키만 암호화됩니다. localStorage와 HTTP 캐시는 평문으로 남으므로, 토큰을 localStorage에 두는 사이트의 로그인은 디스크에서 읽힐 수 있습니다.

### 구현 전 확인 결과

Electron 45.2.2, 샌드박스를 켠 이 서버의 Xvfb에서 임시 프로그램으로 측정했습니다. 앱 코드나 프록시를 거친 측정은 아니며, 키링과 실제 화면 잠금, Wayland, macOS는 시험하지 못했습니다.

| 항목 | 측정 결과 | 설계에 주는 영향 |
|---|---|---|
| 쿠키 암호화 기본값 | fuse가 꺼져 있고, 저장 프로필 쿠키가 `Cookies` DB에 평문으로 저장됨 | 저장 프로필에는 fuse가 필수 |
| fuse를 켠 복사본 | 쿠키가 `v10`으로 저장되어 평문이 사라짐. 다만 키링이 없으면 공개된 고정 키로 복호화됨 | 키링 없으면 비활성화하는 결정이 맞음 |
| fuse로 보호되지 않는 데이터 | fuse를 켜도 localStorage와 HTTP 캐시 파일에 평문이 남음 | 프로필 보호는 쿠키에 한정 |
| 서비스 워커 | 페이지를 `about:blank`로 옮겨도 워커는 약 28초간 전송을 계속함. 저장소 정리 후에는 14회 시험 모두 전송 없음. 쿠키는 유지됨 | 시작 순서 3번이 필요하고, 정리가 끝난 뒤에 개방 |
| 입력 감지 | `input-event`가 합성 키보드와 마우스 입력을 받음. 실제 OS 입력은 미확인 | 유휴 판단은 이 이벤트로 가능 |
| 화면 잠금 | `lock-screen` 이벤트는 타입 정의상 macOS와 Windows 전용. `getSystemIdleState`의 `locked`는 미확인 | Linux는 상태 조회를 쓰고, 감지하지 못하면 5분 유휴에 의존 |
| 프로필 삭제 | `clearData`와 `clearStorageData` 후 파일에서 값이 검색되지 않음. 폴더는 남고, 앱 종료 후 폴더 삭제 시 깨끗하게 다시 열림 | 삭제 표시 후 다음 시작 때 세션을 열기 전에 폴더 삭제 |
| 팝업 (현재 코드) | `window.open`이 창을 돌려주지 않고 `opener`가 없으며, 원래 페이지가 팝업으로 바뀜 | 팝업 로그인에는 변경 필요 |
| 팝업 (허용) | `opener.postMessage`가 전달되고 세션이 같으며 요청 차단을 거침. `did-create-window`가 첫 요청보다 먼저 옴 (1회 관찰) | 설계대로 가능. 자식 창마다 `protectPage` 적용 |
| 패스키 | IP 주소 페이지라서 `SecurityError`가 났고, 동작 여부는 판단하지 못함 | 보장하지 않는 결정 유지 |

첫 서비스 워커 측정은 앞선 세션의 워커가 섞여 정리 후에도 전송이 이어지는 것처럼 보였습니다. 세션별로 다시 잰 위 결과만 유효합니다. 워커의 전송 간격이 300ms이므로 더 짧은 전송은 측정 범위 밖이고, 프록시를 포함한 측정은 완료 조건의 `e2e:security`에서 합니다.

### 구현 순서

1. `egress.ts`의 로그인 모드 상태와 단위 테스트
2. 임시 세션의 로그인 모드, 팝업, 호스트 선택, 패널 화면
3. `request_login` 도구, 디버거 재연결, 로그인 중 도구 거부
4. 저장 프로필과 프로필 선택
5. 실제 사이트 검증

### 완료 조건

- **`npm run e2e`:** 여러 도메인과 팝업을 쓰는 가짜 로그인 픽스처로 시작, 동결, 재개, 호스트 선택, 에이전트 재개를 확인합니다.
- **`npm run e2e:security`:** 대조 세션과 함께 다음을 측정합니다. 앞선 페이지 서비스 워커의 전송, 개방 중 사설 IP와 루프백 접근, 동결 후 새 호스트, 종료 후 요청 차단과 프록시 복원, 에이전트 실행 중 팝업.
- **실제 사이트:** 사용자가 Mac과 Mac의 Linux 가상머신에서 Google과 GitHub를 확인합니다. 직접 로그인, 팝업 로그인, 동결 중 휴대폰 인증 완료, 재시작 후 프로필 유지, 실제 키보드와 마우스 입력 감지, 화면 잠금 감지, 키링을 쓴 쿠키 암호화를 봅니다. 이 서버는 화면이 없고 데이터센터 IP라 쓰지 않습니다.

## 기존 코드 재사용

| 파일 | 처리 |
|---|---|
| `src/policy.ts` | 그대로 사용 |
| `src/ax.ts` | 그대로 사용 |
| `src/tools.ts` | 도구 정의와 `ToolExecutor` 유지, 승인 사이트를 EgressGuard 허용 목록과 연결 |
| `src/agent.ts` | 메인 프로세스로 이동 |
| `src/browser.ts` | `Browser` 인터페이스 유지, 구현을 `webContents.debugger` + `GatedCdp`로 교체 |
| `src/sidepanel.ts`, `src/background.ts` | 새 화면으로 교체 |
| `test/` | 유지하고 전송 통제와 CDP 허용 목록 테스트 추가 |
| `e2e/run.mjs` | 가짜 API와 픽스처 사이트 방식은 유지, 디버깅 포트로 앱을 구동. Playwright의 Electron 실행기는 `--no-sandbox`를 붙이고 이 앱에서 멈춰서 쓰지 않음 |

`tools.ts`의 사이트 승인은 현재 이동이 일어난 뒤에 확인하기도 합니다(`afterAction`). 새 구조에서는 EgressGuard가 요청 전에 막으므로, 허용되지 않은 사이트로의 이동은 요청이 나가기 전에 멈추고 승인을 묻게 됩니다.

## 구현 단계

1. **앱 뼈대 (완료):** Electron 앱, 작업 하나, `GatedCdp`, 기존 도구 연결. 가짜 API E2E 통과. 실제 Claude API로는 아직 실행하지 않았습니다.
2. **격리와 전송 통제 (완료):** 작업별 세션, 요청 차단, 허용 목록 프록시, WebRTC 정책, DNS 차단. 호스트는 정확히 일치해야 하며, 차단된 호스트는 패널에서 사용자만 허용할 수 있습니다. 실제 사이트는 `example.com`만 확인했고, 여러 도메인을 쓰는 사이트는 아직 테스트하지 않았습니다.
3. **로그인 (구현 완료, 실제 사이트 미검증):** 직접 로그인 흐름, 로그인 모드, 로그인 중 에이전트 정지, 저장 프로필. 설계는 위의 "3단계 설계: 로그인"에 있습니다. 가짜 픽스처 E2E와 보안 측정은 통과했고, Mac과 Linux 가상머신의 실제 사이트 확인이 남았습니다.
4. **화면:** 작업 목록, 승인 창, 차단 내역 표시.
5. **외부 연결:** Unix 소켓과 MCP/CLI 브리지. 내장 에이전트와 같은 테스트를 외부 경로로도 실행.
6. **Linux 배포:** Ubuntu 24.04의 `apparmor_restrict_unprivileged_userns` 제한을 풀 패키지(.deb 설치 시 SUID `chrome-sandbox` 또는 AppArmor 프로필) 구성. 실제 Linux 데스크톱에서 로그인 재검증.
7. **macOS 지원:** 코드 서명과 공증.

Linux 로그인은 막히면 설계에 영향을 주므로 6단계까지 미루지 않고, 3단계 완료 조건에서 Mac의 Linux 가상머신으로 확인합니다. 서버에 원격 화면을 붙이면 요청이 데이터센터 IP로 나가 결과가 달라질 수 있습니다. 6단계에서는 패키지를 설치한 실제 환경에서 다시 확인합니다.
